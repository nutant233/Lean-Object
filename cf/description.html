Lean Object makes Minecraft's most-used lookup objects cheaper, by deduplicating them. When a value exists exactly once, comparing it becomes a pointer compare instead of a string compare — and that comparison happens on every registry lookup, tag check and ingredient match.

For Minecraft 1.21.1 / NeoForge. Requires Java 21 and NeoForge 21.1.169 or newer.

Why deduplication makes things faster

A hash code only picks the bucket. Every collision inside that bucket is then resolved with equals(), and that is where the expensive work happens — for a TagKey, comparing a ResourceKey and a ResourceLocation, i.e. string chains. Modded packs make this worse: thousands of identifiers sharing prefixes like minecraft: or mymod: have hash codes that cluster, so the buckets where comparisons pile up are exactly the busy ones.

Keep only one instance per logical value, and equals can be reduced to o == this and hashCode to System.identityHashCode. Every one of those comparisons becomes a pointer compare. Less memory is a side effect of the same change, not the goal.

Features

All features are on by default and can be switched off individually in config/leanobject.toml.

FeatureWhat it does
ResourceLocation One instance per namespace:path. Duplicate instances and their strings disappear, and equals/hashCode become identity based, so registry and model lookups compare pointers. A non-destructive mode keeps value comparison while still sharing instances.
TagKey Custom interning replaces the vanilla interner, and equals/hashCode become identity based. Tag membership tests are the hottest path in most packs.
ResourceKey Replaces vanilla's interning map with a leaner one, so registry keys are built with a single cache probe instead of filling a ConcurrentMap. Identity comparison is already how 1.21.1 keys behave, and stays that way.
Ingredient Single-entry ingredients reuse one shared instance, so recipes stop rebuilding identical Ingredient objects and their lazily built item arrays.
NBT containers Replaces the maps and lists inside CompoundTag, ListTag and NBT record building with leaner equivalents.
Model objects Leaner containers for baked block and item models. Client side.
AE2 storage keys Deduplicates AE2 AEItemKey / AEFluidKey, and replaces the hash AE2 caches in its constructor with the identity hash. Requires AE2.

Playing a tech pack? Turn on AE2 key deduplication

Official AE2 has no interning for storage keys — AEItemKey's constructor is private and every factory builds a new key object. A late-game ME network is little but keys: banks of interfaces, storage buses, import/export buses and crafting CPUs hold enormous numbers of them, all allocated on demand and compared by value.

That is exactly the workload this feature targets, and it speeds up key creation, not just key lookup:

  • Vanilla allocates a new key object and hashes its components in the constructor, storing the result in a final field that hashCode() merely returns.
  • With this mod, a key without components becomes a field read: the shared instance is fetched from the item, with no allocation and no hashing at all.
  • A key carrying components costs one cache probe keyed by the component patch, and that is the entire cost. Only the first probe for a given patch allocates anything; repeats return the existing key.
  • The hash the constructor computes is replaced with the identity hash at the point it is computed, so the cached field and hashCode() stay consistent with identity comparison.
  • All the other factories are routed through the same cache too — the packet reader, and the codec factory that NBT and JSON parsing both go through.

In a modded pack this happens constantly. AE2 rarely works on its own storage: storage buses, import and export buses and interfaces connect the ME network to other mods' inventories — chests, barrels, machines, drawers, pipes — and every item moved across that boundary is converted between an ItemStack and an AE key. Those transfers run continuously in bulk, per item, per bus, per tick. A shared instance per logical key turns that conversion into a cache probe instead of an allocation plus a hash.

Supersedes Fast Tag

Lean Object replaces Fast Tag and is meant to be used instead of it. The TagKey and ResourceKey features come from it — the same methods are replaced, with the same reasoning, and interning keys are compared by reference in both. What changed is the cache backend: Fast Tag used Guava's MapMaker and reflection into its internals, Lean Object uses its own caches with plain identity maps and no reflection.

Do not install both. They replace the same methods, and the last one applied wins.

Configuration

config/leanobject.toml is regenerated on every launch:

enabled = true          # master switch
loggingInGC = true      # force a GC and log heap usage when joining a world

[features.tagKey]
    safeMode = false    # false = replace the methods, true = wrap the original ones
    enabled = true

safeMode applies to the features that ship a non-destructive variant (resourceKey, tagKey, resourceLocation). Set it to true if another mod conflicts with the replacing path — it wraps the original methods instead. For resourceLocation that also means equals/hashCode stay value based, which is the conservative combination.

Compatibility notes

  • FerriteCore is handled automatically. FerriteCore's ModelResourceLocation cache and this mod's resourceLocation feature replace the same call, and two replacements cannot both inject — so FerriteCore's option is switched off while this mod owns that path. Requires FerriteCore 7.0.2 or newer, the first version that lets another mod do this.
  • Injection conflicts. Most features replace methods outright. If another mod modifies the same target, the two fight and the last one applied wins. The model feature in particular is known to conflict on large packs; it can be turned off on its own.
  • Reference equality. Interned keys compare by reference, so a value created outside the interning entry points will not compare equal to its interned twin. In 1.21.1 nothing in Minecraft or NeoForge constructs a ResourceLocation directly, so this only concerns mods that reach the constructor through their own access transformer.
  • AE2 support is version specific. It targets official AE2 19.2.17 and hooks private members of AEItemKey/AEFluidKey. Forks or other builds can change those internals, in which case the feature fails to apply loudly instead of misbehaving.
  • Optional integrations are auto-detected. Features whose mod is not installed are skipped automatically.
  • No Farmer's Delight support on 1.21.1. The 1.20.1 line has a farmersDelight feature that caches ToolActionIngredient; Farmer's Delight has no 1.21.1 build this port could compile against, so there is simply no such feature here. Recipes are parsed exactly as they would be without the mod.
  • ResourceLocation interning costs CPU as well as saving memory. It is constructed extremely often, and interning adds a cache probe to every construction. It pays off when the same id is created repeatedly; it can cost CPU on hot paths that keep producing distinct ids, where nothing gets shared. If you are chasing CPU rather than memory, try turning this one feature off first.
